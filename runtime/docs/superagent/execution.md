# 执行器、Git 集成与逐阶段恢复

端口类型采用 [ExecutionPort](contracts.ts)，业务状态采用 [storage.md](storage.md)。执行器负责全部文件、命令、终端和后台进程入口，模型无法通过选择另一个原生工具绕过策略。

## 1. 平台实现与依赖

| 执行设备 | 规定后端 | 进程与策略边界 |
|---|---|---|
| Linux x64/arm64 | `@anthropic-ai/sandbox-runtime` 精确锁定 0.0.81，bubblewrap 至少 0.5，socat、ripgrep | 每个执行会话一个独立 helper 与策略；进程组归 helper 所有 |
| macOS arm64/x64 | 同版本 sandbox-runtime，系统 sandbox-exec、ripgrep | 每会话独立 helper；文件与网络策略分开提供，禁用 Apple Events |
| Windows x64/arm64 | Docker Engine API 1.45 或兼容版本，dockerode 客户端 | 每会话独立容器；镜像按 digest 固定，项目选择实际 linux/windows 执行系统 |

Linux/macOS 使用库提供的文件与网络执行策略，配置必须显式给出读写与网络规则。Windows 使用容器独立文件空间，主机只映射当前任务、只读 Git 对象和只读参考资料；Docker socket、宿主用户目录与 DSH 数据根均不映射。Docker daemon 仅由可信执行服务访问。主机架构、镜像 OS 与项目 executionOs 不匹配时返回 executor-unavailable，不切换系统运行。Windows 容器使用与宿主兼容的版本和隔离方式，由能力检测实际启动验证后记录。

Linux/macOS 也允许用户明确选择 Docker 执行环境，executionOs 使用实际镜像系统。srt 对应宿主本地系统，Docker 对应容器系统，二者分别验证能力；系统无法满足某一后端的要求时直接拒绝该配置。项目工具链需要的操作系统在启用表单和任务详情展示。

Linux/macOS 的 helper 在宿主私有工具目录安装和运行，Worker 无写权限；每个 helper 使用独立 SandboxManager，避免并发任务共享全局配置。弱化嵌套隔离、Apple Events、全部 Unix socket 与较弱网络隔离均关闭。系统临时目录不作为本项目的中间结果位置，`TMPDIR/TEMP/TMP` 指向任务 scratch，系统默认便利写入路径显式加入拒绝清单。配置不完整或底层 seccomp/命名空间无法满足要求时返回 isolation-unavailable。

Docker 默认 NetworkMode=none。需要网络的项目由用户明确配置 `kind=network`，界面显示“允许任务访问网络及其可达服务”；该授权不表示域名过滤。容器只得到任务指定的外部服务凭据，无法取得用户命令密钥。domains 策略用于 srt，并固定 strict allowlist；Docker 不接受 domains 配置，不能将其解释为全部网络。Linux/macOS 的 network 策略也不被隐式解释成宽泛域名规则。

Node 与执行辅助程序打包在宿主只读安装目录。Git 客户端使用 simple-git，差异产生、树合并、索引、对象和引用操作使用原生 Git。SQLite 使用 Node 内置实现。所有实际依赖版本写入 lockfile，SRT 版本保持本节精确值；升级先重新执行本文件与 SA 验收，不能仅靠版本范围宣布兼容。

受信任的文件封存与应用使用宿主包内独立的 Rust 辅助程序，文件访问依赖 cap-std 4.0.3，并通过 Cargo.lock 固定传递依赖。该程序只接受宿主建立的目录能力和已验证的文件计划，使用相对目录操作、文件同步与重命名；不解释模型脚本。各平台二进制随宿主产物交付，能力探测核验其版本、摘要与目录限制。构建环境需要对应 Rust 工具链，运行设备使用已打包产物。

## 2. 文件访问与参考目录

执行目录位于设备数据根 `superagent/work/<projectId>/<taskId>/<attemptId>/<sessionId>/`，包含 `repo` 和 `scratch`。配置、SQLite、用户授权密钥、其他任务和业务对象库位于 Worker 读取范围之外。会话只允许读取当前代码、授权输入、登记参考资料及执行工具所需系统目录。

设备数据根必须位于项目目录和参考目录之外，配置检查拒绝互相包含的路径。helper 的 Node 临时目录设置为当前 scratch，Worker 的 HOME 及包缓存也指向自己的 scratch。拒绝读取宿主数据根与用户目录后，只重新允许当前任务、固定基准对象目录、获准输入目录、批准参考来源和具体系统工具目录；系统凭据、管理 socket 与私有服务密钥不在允许集合中。

srt 文件规则对用户目录、运行时私有目录与其他工作目录建立读取拒绝，单独允许本任务和实际工具路径；写入只允许当前 repo、scratch 和批准的缓存路径。参考来源和其真实路径始终拒绝写入。文件工具在宿主侧验证真实路径，其实际打开、读取与写入在受管 helper 或容器中执行；终端及子进程使用相同操作系统策略。受信任的封存和应用辅助程序使用目录能力约束实际打开，拒绝越界链接和路径替换；成果只封存声明文件，不把映射目标打包。

Windows 将当前 repo、scratch 挂载为可写，将共享来源挂载为只读。映射不可覆盖仓库已经跟踪的路径。挂载源被删除或替换时重新检测实际目录身份，不在新来源上自动沿用权限。原始参考资料保持实时共享；读操作记录来源和读取摘要，目录更新不触发完整复制。

任务初始文件使用 Git 检出或普通文件复制建立，禁止使用可能给外部文件增加可写别名的硬链接。参考资料中的既有硬链接只存在于只读范围，不导入任务可写目录。用户或外部程序在任务目录放入未经登记的外部链接时，任务封存与后续执行检查明确拒绝。

进程里的所有 Git 命令使用宿主生成的环境，不继承用户管理凭据。宿主 Git 服务关闭自动维护、外部 diff、未批准的过滤器和隐式凭据助手；需要的 LFS 与签名程序由项目执行配置显式声明。Git 配置与钩子目录对模型命令只读。文件工具可以修改任务内的项目源文件，包括 .gitmodules；宿主 Git 服务在应用准备时验证其含义，模型不能借此改变宿主 Git 配置。

## 3. 任务代码准备与输入封存

1. 在任务创建事务中记录真实 Git 对象格式、HEAD 或 empty、目标本地分支及配置版本。以宿主私有引用固定已有提交，防止任务仍使用对象时被自动回收。
2. 宿主按基准提交建立不可变 Git 基准对象库，使用原生 pack-objects 只导出该提交可达的对象。原项目对象目录包含暂存内容、其他任务或未批准对象，不能直接暴露给 Worker。相同基准可以共享一个只读对象库；每个执行会话建立独立 Git 副本，拥有自己的索引、HEAD、引用和新增对象目录，只通过只读 alternates 读取获准基准。Git 元数据由 Git 命令生成，禁止手工解析或重写对象、索引格式。跨宿主与容器路径由执行器内的 Git 准备程序创建，不能留下宿主不可解析的对象路径。
3. 有提交时检出记录的对象；empty 时使用空索引和无历史分支，不在项目建立占位提交。项目原有未提交和未跟踪代码不自动读取进任务。引用目录映射在检出之后安装，并登记为成果排除路径。
4. 对已批准依赖按 DAG 顺序交付固定成果。每项成果保存 effectiveBaseTree、outputTree 和由 Git 生成的完整二进制 patch。消费任务的 effectiveBaseTree 包含这些输入，自己的成果 patch 只记录相对于该输入的新增变化，避免重复纳入上游修改。
5. 同任务子代理取得父 Worker 已封存的输入树和任务权限。修改型子代理建立独立副本，内部结果整理进入父任务，跨任务输入依旧检查原授权。
6. 在同一执行器里运行项目 prepareCommands。依赖、缓存和配置使用批准的任务范围，准备超时或失败停止当前尝试；不改用原项目目录继续运行。

基准对象库只由宿主服务创建，发布后保持不可变。任务新增对象、已批准依赖对象和子代理输入进入各自的私有目录；审阅计算对象、原项目索引对象与其他任务未批准成果不进入基准对象库。执行角色即使枚举全部可见 Git 对象，也只能取得自己的基准和已授权内容。LFS 内容与子模块对象按固定版本准备并验证；缺失、权限或网络条件不足时等待用户配置。共享引用、scratch、缓存、Git 管理文件与凭据不纳入成果。正常新增文件通过明确的成果路径集合登记，Git ignored 的代码或制品必须在成果选择中明确列出后才封存。

容器和宿主使用不同路径时，工作副本的 Git 操作全部在对应执行器中完成。成果服务通过原生 Git pack-objects 导出树和 blob，再由宿主在私有对象目录用 unpack-objects 导入，标准流由成熟客户端处理。审阅 patch 保留原生 Git 生成的格式，宿主依据清单和实际树处理内容。宿主导入源项目对象前通过同一可信 Git 服务核验对象格式与摘要，原项目分支只在用户授权的发布阶段更新。

## 4. 进程、服务与工具调用

每次调用先验证 actor、代次、策略 revision 和资源预留，再启动受管进程。argv 通过结构化参数传递；用户代码需要 shell 时仅在执行器内启动指定 shell。stdout/stderr 流式分页存入受认证的执行记录，遥测不记录原文。终端由相同执行器创建，禁止额外的宿主直连终端。

启动环境使用显式允许清单，保留所需系统工具路径和任务变量。用户访问令牌、节点命令密钥、DSH 管理凭据、模型提供方密钥和宿主代理凭据不继承到执行进程。项目批准的外部服务凭据从宿主凭据服务按具体用途提供，不能通过普通环境转储读取宿主全部配置。

srt helper 监听宿主管理管道，宿主退出或策略撤销时停止其进程组。Docker 容器带 project/task/session/generation 标签，重连按容器 ID 与创建时间核验。进程数量与磁盘使用由运行时和执行器双重检查；未确认结束的进程继续计入资源。停止超过 stopConfirmMs 时返回 stop-unconfirmed，后续只查询原进程；用户界面不能提前显示终止。

taskProcessCount 在启动受管入口前原子预留，约束命令进程组、终端和作业的并发数量。系统子进程仍属于原执行体，停止确认必须覆盖全部后代，包括尝试脱离原进程组的进程；不能证明回收能力的后端不通过能力检测。磁盘阈值每 resourceProbeMs 检测，达到阈值后停止新写入入口并终止当前任务写入进程。采样期间可能超出阈值，界面将其标为运行时使用阈值，文件系统硬配额由设备实际存储配置单独报告。

原生 FS、bash、pwsh、terminal、jobs 和 browser 的实际执行注册在会话 setup 中替换为受管适配器，并在 Agent 发布前完成。宿主层可见工具另外受角色过滤。宿主 MCP 工具按调用方法校验；会写入文件的调用必须定位到任务目录，外部写操作执行原工具审批。浏览器在任务执行环境使用自己的 profile，桌面控制工具不提供给执行角色。

PTC 的 run_code 脚本在本会话执行器中运行，工具调用通过带会话身份的受管通道返回宿主，禁止在宿主进程直接解释 Worker 脚本。宿主只接受绑定到该会话与当前代次的工具能力，不传递用户命令身份。工作目录切换、原生会话创建、配置管理和未包装的子代理工具不进入 Worker 目录。

externalToolIds 默认空集合。MCP 和连接器工具必须具有可验证的读取、文件写入或外部副作用声明，项目明确允许后才对执行角色可见。文件写入接口验证真实目标仍在任务范围；未分类的工具不进入该模式工具目录。外部副作用保留实际工具审批，模型不能通过一个通用代理工具获得未登记能力。

外部工具的网络目标还要满足项目网络策略；deny 不允许执行具有网络访问的工具，domains 只能交付可验证目标的调用。不提供目标约束能力的通用远程执行工具无法用于 domains 模式。受信任模型入口、任务状态通道与遥测使用宿主内部服务连接，执行角色无法通过这些连接指定任意目标或发送工具调用。

封存成果前停止该版本的写入并核验所有后台写入者状态，取得任务写入锁，使用全新私有索引从实际文件构造输出树。每个文件读取前后核对状态，目录清单也再次核对；存在竞争则返回 resource-busy。验证证据必须来自宿主记录的真实进程、退出状态与实际输入树，模型传入的文字不能构造 passed 证据。成果产生后保持不可变，后续修改只产生新版本。

任务可登记具名独占资源，例如测试数据库或服务端口。Engine 在准备阶段预留，结束后确认释放；同名资源排队，暂停但仍有活跃服务时保留实际占用。项目范围或设备范围由配置明确指定。权限收紧后现有进程必须终止并按新策略重建，不能假定更新 JSON 已改变现有操作系统权限。

## 5. 审阅候选与应用算法

### 5.1 生成候选

宿主取得仓库级应用准备锁，读取 `H`（当前目标提交或空树）、`I`（原索引树）、`W`（相关工作文件）及原始索引字节。索引存在未合并项、分支或文件系统存在大小写冲突时返回具体冲突。索引树通过私有 GIT_INDEX_FILE 副本创建，原始索引保持不变。

合并操作使用原生 `git merge-tree --write-tree --no-messages --merge-base=<baseCommit> <oursCommit> <theirsCommit>`。宿主在私有计算仓库将实际输入树用 commit-tree 关联到内部计算提交，显式指定三方基准。计算提交使用固定宿主身份，按树与算法版本复用，只保存在宿主私有计算对象目录；原项目历史只接收用户批准的真实提交。empty 使用 Git 产生的空树，内部计算不会在无提交的项目建立占位提交。

以 H 为初始候选树，按依赖顺序将每项成果的 effectiveBaseTree、当前候选树、outputTree 作为三方输入，得到仅含批准成果的树 `R`。同一依赖已存在于候选时由原生树合并保留实际结果，重命名和二进制也遵循同一算法。已经应用后又被用户修改的内容参与真实三方合并，冲突立即结束准备；宿主不会重新覆盖整份上游目录。依赖授权、成果版本和实际变更共同写入审阅清单。

自动补入的上游依赖如果已有成功 apply_commit 记录，且 Git 确认该提交是当前 H 的祖先，则记录 previously-applied 并保留 H 中的实际内容，继续合并消费任务相对于其固定输入的增量。上游经过钩子或用户后续修改时记录 changed，展示原输入、已应用版本与当前版本。只应用到工作目录、尚未进入 H 的依赖仍纳入本次批准的提交闭包。用户显式选择的成果与自动补入的依赖分别登记，所有依赖授权继续有效检查。

再以 H 为共同基准，分别合并 I 与 R、W 与 R，得到 `I'` 与 `W'`。任何三方冲突直接进入审阅冲突状态。`I'` 保存用户原暂存内容与成果的组合；发布 R 后，R 到 I' 的差异仍表达用户原暂存意图。W' 保存用户其他未提交内容。只执行 apply 时保留原暂存树 I，新增成果作为未提交文件变化出现。

候选索引从原始索引的私有副本生成。在原仓库上下文中以 GIT_INDEX_FILE 指向副本，使用原生 update-index --no-split-index 读取共享索引依赖，再用 read-tree -m -i 写入最终树。未受影响的 intent-to-add 路径通过成熟 Git 状态客户端取得并使用原生 add --intent-to-add 保留。未受影响的 assume-unchanged、skip-worktree 标记保留；此次实际材料化的文件按明确计划清除必要标记，变更进入审阅摘要。稀疏检出中未出现的文件以索引内容参与计算，不能误判为用户删除。索引版本、扩展与共享文件均交给 Git 处理，禁止复制新仓库的索引覆盖用户索引元数据。

merge-tree 退出码 0 才接受其单个树标识，并用 Git 核验对象类型；退出码 1 保存完整原生冲突证据，其他退出码记录实际执行错误并终止。冲突原文作为不透明业务证据展示，文件版本从已保存输入树通过 Git 客户端读取，禁止自行解析多段输出或根据冲突标记推断文件清单。候选目录使用 Git 从计算树建立，完整 patch 仅作为原生 Git 生成的审阅与导出内容。

在 R 与 W' 的隔离目录执行规定验证，分别记录“提交内容验证”和“当前工作内容组合验证”。失败时展示真实结果，不自动修复用户其他修改。目标相关文件、原索引、分支、钩子来源、依赖授权、验证配置的摘要共同构成 ReviewView。未受影响的普通文件编辑无需阻止准备，实际会修改的路径及完整索引必须被核验。

Git 对象、路径、引用、索引和授权检查始终执行。verifyCommands 为空时明确显示“未配置项目验证命令”，用户仍可审阅并决定应用，不能记录为项目测试通过。已配置命令必须全部成功才能发布 ready 审阅；命令结果未知时保持未确认并查询原进程。

apply_commit 候选执行项目要求的 pre-commit、prepare-commit-msg、commit-msg 校验，通过原生 Git hook 入口在候选目录运行，得到的代码与消息变化包含在最终审阅版本中。apply 候选执行规定项目验证。钩子执行受相同权限和网络策略约束。用户编辑提交信息后重新准备相应消息校验。post-commit 中的外部动作单独显示并授权，不能借本地提交隐式执行推送。

钩子修改文件后重新生成最终 R，并用最终成果变化重新构建 I'、W'，再次执行相应验证；钩子修改消息后重新核验最终消息。所有最终对象固定之后才发布 ready 审阅。钩子反复产生不同结果或候选无法通过验证时返回 hook-failed，保留实际证据，禁止展示与即将应用的内容不同的审阅。

### 5.2 执行用户决定

| 阶段 | 操作与耐久要求 |
|---|---|
| preparing / prepared | 固定 R、I'、W'、原索引和逐文件 before/after 对象，fsync 后登记数据库 |
| authorized | 校验 human 操作、review revision、摘要、实际 HEAD/分支/索引和受影响路径；消费一次审阅版本 |
| files_applying | 获取项目写入锁和原生 index.lock，逐文件核对 before 后使用同目录临时文件及原子重命名写入 after；每次写入后同步文件、父目录与阶段记录 |
| files_applied | 核验所有受影响文件符合 W'；检测到外部修改时保留实际阶段并停止 |
| index_applied | apply_commit 使用以原始索引为基础生成的 I' 索引并同步；apply 保留原暂存树，只执行审阅明确的材料化标记变更 |
| ref_published | apply_commit 创建以 H 为父、树为 R、审阅消息与明确作者身份的真实提交，使用 update-ref 的旧值比较交换发布；empty 要求目标引用仍不存在 |
| verified | 核对项目分支、提交树、实际文件与暂存意图；记录验证证据 |
| completed | 将成果关联到完成任务，返回 commitOid 或应用结果，提交操作结果与事件 |

创建提交对象使用 Git commit-tree 和项目明确的签名设置；必须先执行并验证上述项目校验钩子。签名由宿主受信任的签名程序完成，私钥不提供给候选代码。创建对象与发布引用的阶段分别记录，发布后不重复创建提交。提交对象可以在 files_applying 前创建并持久记录，以便整个操作使用同一个对象；用户授权必须已经有效。

targetRef 必须等于项目当前 HEAD 的符号引用，H 同时固定该分支的提交。detached HEAD 的 apply 候选使用 HEAD 作为目标标识，按原暂存树与文件计划执行；apply_commit 要求用户先选用本地分支。apply 在 index_applied 后直接进入 verified，不生成提交对象或引用发布事实。

索引使用原生锁协议，项目普通文件工具在应用期间等待同一写入锁。外部编辑器无法纳入应用内锁，因此每次实际写入前后核对内容；发生竞争时显示真实部分完成情况，不能承诺多文件操作具有一次原子写入语义。符号链接写入只创建记录的链接内容，不跟随目标；重命名、文件模式与大小写变化通过明确的文件计划执行。

实际文件计划由受信任辅助程序在已打开的项目目录能力下执行，逐项保存并核验文件身份、内容和模式。路径被替换、目录被移动或链接指向授权范围之外时停止当前计划并记录冲突；源目录的稳定身份与审阅记录不一致时拒绝写入。Windows 文件占用使原子替换失败时保留原阶段，不改用直接截断文件的方式完成写入。

子模块的审阅包含其独立成果与父 gitlink，按依赖先发布子模块提交，再应用父指针；每个仓库有自己的应用记录，共用一个用户授权的成果闭包。中断时分别展示已发布事实，不隐藏部分完成。LFS 先核验并保存需要的对象再发布指针，远端上传使用独立授权。所有成果差异包含实际进入提交的对象和文件模式。

恢复时按 [存储恢复表](storage.md)逐项检查。恢复原文件使用记录的文件内容和权限，通过文件操作执行；主项目工作内容没有 Git reset、checkout、restore 或 revert 恢复路径。源分支已经发布时，后续修复形成明确的新操作与成果。

## 6. 能力探测与兼容验收

probe 在项目内的已忽略独立验证目录或设备专用测试数据根使用真实进程完成：当前任务目录可写、主项目与参考目录不可写、其他任务及宿主私有数据不可读、管理 socket 不可达、网络规则实际生效、进程树可终止、Git 索引与引用相互独立。探测对象不使用真实凭据，受保护探测文件使用真实文件权限和执行器。任一必要条件失败即返回明确错误，不运行未隔离命令。

Git 最低版本为 2.43；同时探测实际对象格式、空仓库、二进制与重命名树合并、索引锁和 CAS 引用。DSH 仓库基线见兼容文档，适配层必须验证 Agent create/resume/setup、稳定 inbox 标识、handle 销毁与子代理事件。较新本机 API 无法证明基线可用；缺少接口时在适配层实现等价的持久投递与角色限制，并通过同一组真实验收。

执行能力结果记录 backend、版本、平台、配置摘要和证据引用，不记录主机名与内网地址。能力变化立即使相关准备状态失效。Linux、macOS、Windows 每个平台都执行真实正向与拒绝测试，缺少平台时相应功能验收保持未通过。
