# 桌面控制设计评审记录

本文件记录桌面控制（computer use）方案的一次独立评审：评审范围、实测基座、各评审角色的结论、发现项与处置结果、以及评审后落定的决策。设计正文见[架构设计](architecture.md)第 7.8 节，本文件只记评审过程与结论，不复述设计要求。

## 一、评审对象

评审针对 7.8 节当时的最新版本，覆盖三项文件：`docs/architecture.md` 的 4.5 节、7.8 节与第十二节验收方式，`docs/deployment.md` 的执行节点段落，`docs/desktop-mobile.md` 的承诺边界与平台段落。

被评审的设计要点：桌面控制复用 DSH 内置的 `@deepseek-ai/dsh-computer-use` 服务与 `@deepseek-ai/dsh-experimental-computer-use-cua-driver-native` 提供方，底层为 `@trycua/cua-driver`；支持 macOS 与 Windows，不支持 Linux 图形界面操作；提供方自带 59 个工具，产品侧按白名单收敛；默认关闭，按会话开启并重新确认。

## 二、评审方式

五位独立评审角色并行审阅，各自只看一个维度，互不通报结论，最后汇总比对。评审角色与职责如下。

| 角色 | 职责 | 结论 |
|---|---|---|
| 技术事实评审 | 逐条核验文档里的技术断言，与实物对照 | 完成，指出两处阻断级事实错误 |
| 一致性评审 | 检查三份文件改动后的内部矛盾与交叉引用 | 有条件通过 |
| 安全与权限评审 | 审查安全模型、审批机制、权限归属 | 未完成，中途停摆 |
| 工程可实施性评审 | 审查分发、维护、许可证、升级路径 | 不通过 |
| 产品与用户影响评审 | 审查用户可见的能力边界、体验与承诺 | 有条件通过 |

安全与权限评审在长时间检索后停在半途，没有产出结论。该角色负责的机制问题由主评审用同一批实物与 DSH 源码复核补齐，逐条列在第四节，每条注明是复核得出。两位角色独立命中同一批阻断项，交叉验证的可信度据此成立。

## 三、实测基座

评审结论建立在实测之上，不采信二手说法。以下数据可复现，来源为本机 npm registry、GitHub API 与解包后的原生库。

**候选模块的现状。** robotjs 0.9.1（2026-08-07 发布）已改为 Node-API，按六个平台发布预编译产物，仓库近十二个月 70 次提交。`@nut-tree/nut-js` 在 npmjs 官方 registry 返回 404，仓库 2024-05 之后零提交。`uiohook-napi` 只做全局事件监听，不含注入与采集。这套数据推翻了「robotjs 多年不更新、没有预编译产物」这一原始前提。

**内置提供方的现状。** `@deepseek-ai/dsh-computer-use` 依赖为空，只提供一个排他注册位；真正提供能力的是 `@deepseek-ai/dsh-experimental-computer-use-cua-driver-native`（0.2.1-rc.2），它把 `@trycua/cua-driver` 锁在 0.28.0，而上游已到 0.36.0。本机 DSH 0.2.1-rc.2 的 86 个依赖里没有 computer-use 相关包，使用这套需要自行安装并在组合里挂载。

**工具目录。** 实测 `listToolsJson` 返回 59 个工具，注册名统一加前缀 `cua_driver_native__`，最长 43 字符，全部符合函数名的字母数字、下划线、连字符与 64 字符上限。其中带 `from_zoom` 参数的只有 7 个指针动作工具，`type_text` 没有这个参数。

**原生库与许可。** Windows 后端为 UIA 加 PostMessage，前台升级用 `SetForegroundWindow`、`SendInput` 与 `AttachThreadInput`；macOS 后端为 AXUIElement、CGEvent 与 ScreenCaptureKit。体积分别为 Windows DLL 25.3MB、macOS dylib 51.5MB、Linux so 42MB。驱动 SDK 为 MIT，运行时依赖 `@ubjs/*` 与原生包内 `cua_driver_node_runtime.node` 为 MPL-2.0。

**DSH 机制。** `ctx.computerUse.register` 是运行时单例，二次注册直接抛出异常。`ctx.tools.restrict` 必须带 scoped context，遇到未知工具名抛出异常。`ctx.tools.guard` 是同步函数、只能返回拒绝理由。审批的正确接缝是 `tools/pre-execute` 瀑布返回 `{ kind: 'ask' }`，由工具运行时调 `ctx.approval.request`。`hasRequiredMacOSPermissions` 需要一个 `MacOSPermissionStatus` 参数。

## 四、发现项与处置

共 25 项，按严重程度分三档。处置结果分两种：已改，指已按发现修改文档；已定，指评审后由决策落定。

### 阻断级

| 编号 | 发现 | 处置 |
|---|---|---|
| B1 | 两行插件在会话 preset 里挂载会撞排他注册位。注册位是整棵运行时的单例，第二个会话启用直接抛出异常；即使不抛出异常，每个会话各起一套原生驱动也会让 25MB 以上的原生库重复加载，且原生段错误会连带终止整个运行时进程。 | 已改。两行改到宿主平面，随进程加载一次；4.5 节写明原因。 |
| B2 | 审批接缝写错。`ctx.tools.guard` 是同步函数，承载不了异步审批。 | 已改。改用 `tools/pre-execute` 返回 `{ kind: 'ask' }`，并写明 guard 不能用于审批。复核得出。 |
| B3 | `from_zoom` 只被 7 个指针工具支持，`type_text` 没有该参数，文档要求它带这个参数会校验失败。 | 已改。限定为 7 个指针工具，`type_text` 改为按元素令牌或窗口坐标定位。 |
| B4 | 分发形态整节缺失。原生库不能从 ASAR 内加载，需解包、保留可执行位、逐文件签名、整包公证，体积增量也未量化。 | 已改。新增「分发形态」段，列出三平台体积与四项强制动作。 |
| B5 | 驱动版本锁死且升级权在提供方，没有升级策略与退出策略。 | 已改。新增「上游版本与退出策略」段，写明精确版本、升级前比对工具目录、以「不挂载即不提供」作为退出口。 |
| B6 | 用户可见的能力边界只写在架构文档里，没有落成开启前预检、错误文案与顶层中断入口。 | 已改。新增「能力边界在开启前就要可见」「用户可见的能力缺口要交代」「截图依赖模型的图像输入」三段。 |

## 五、评审后的决策

三处无法由评审单方面判定，交由产品决定，结论如下。

**决策一：会话级重新确认采用方案 A。** 会话内第一次调用桌面工具时，`tools/pre-execute` 先返回 `{ kind: 'ask' }` 触发一次会话级确认；同意后本次会话记下状态，后续调用逐次授权；状态只活在会话内存，会话结束即失效。选最严的一档，代价是高频用户每开新会话都要确认一次，这与桌面控制被定性为 `danger-full-access` 的一种形态相称。

**决策二：白名单分三档，由用户选择，默认第二档。** 分档依据是动作的破坏半径：一档只动指针、键盘与焦点；二档增加改窗口几何与触发应用菜单命令；三档增加启动任意程序与强制终止进程。切换取较弱一侧生效，提高档位要重新确认，降低档位立即生效。

**决策三：macOS 门槛定在 14。** 驱动主包只承诺 13，且原生包没有 `engines` 声明，门槛必须由桌面壳自行判断。产品抬到 14，理由是 13 上 ScreenCaptureKit 能力不完整、采集路径有可用性风险。同步修改了 `deployment.md` 的 `capabilities` 声明条件与 `desktop-mobile.md` 的承诺边界。

## 六、遗留与后续验证

评审只能在本机 Linux 环境完成，以下项目必须在真机验证，已作为验收条目写进第十二节。

**必须在 Windows 真机验证。** UIA 与 PostMessage 能否在真实窗口点击成功；`delivery_mode: background` 在具体应用上的拒绝情况；向高完整性级别窗口注入是否返回 `background_uipi_blocked`；`SetForegroundWindow` 前台升级是否可靠。

**必须在 macOS 真机验证。** TCC 归属是否沿 responsible process 链记到签名应用；`requestMacOSPermissions` 在主进程调用能否稳定弹窗；ScreenCaptureKit 采集是否正常；`from_zoom` 坐标映射是否精确；签名与公证是否通过。

**必须在打包流程验证。** 原生库是否落在 `app.asar.unpacked`、可执行位是否保留、逐文件签名是否完成、安装包增量是否可接受。

**必须在上游升级时验证。** 提供方版本变化后工具数与白名单命中是否改变；Electron 大版本升级后 copy-mode 运行时能否在 memory cage 下加载。

**观察项。** 提供方为实验性版本，工具 schema 跟随锁定的上游 SDK，不作稳定性承诺。上游驱动从 0.28.0 到 0.36.0 已差八个小版本，升级权在提供方，产品无法独立跟进。这两条决定了桌面控制必须始终保留「不挂载即不提供」这个退出口。
